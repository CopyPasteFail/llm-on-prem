# ADR-0001: One Active vLLM Model for v0.1.0

**Status:** Accepted

## Context

The initial platform runs on one ASUS Ascent GX10 with one GPU. The service is an internal capability alongside existing subscriptions, rather than a critical service that requires zero-downtime model changes or permanent parallel model access.

The design considered serving several distinct base models concurrently through separate vLLM deployments, GPU time-slicing, CUDA MPS, or MIG.

That would enable an always-on production model and an always-on candidate model. It would also divide one GPU's compute and memory capacity, add capacity tuning and failure-mode complexity, and make production latency less predictable. Some sharing modes also do not provide the isolation expected from separate physical GPU capacity.

## Decision

Version 0.1.0 serves **one active GPU-backed vLLM base model at a time**.

The vLLM Deployment:

- Runs one replica.
- Requests the full GPU with `nvidia.com/gpu: 1`.
- Uses the Kubernetes `Recreate` deployment strategy.
- Does not use GPU time-slicing, CUDA MPS, or MIG as a version-0.1.0 requirement.

The platform exposes one stable model alias, `company-code`, through LiteLLM. Clients keep using the same endpoint and alias when the underlying model changes.

A model evaluation is a controlled model replacement:

1. Change the pinned model-release values in Git.
2. Let GitLab CI validate the Helm chart and rendered manifests.
3. Merge the approved desired-state change.
4. Let Argo CD reconcile the Helm release.
5. Allow the replacement vLLM pod to load the candidate model.
6. Run smoke tests and user evaluation.
7. Keep the model or revert the Git change.

Rollback is a Git revert that restores the prior known-good model-release values. Argo CD then reconciles Kubernetes to that prior desired state.

## Rationale

This choice intentionally favors predictable operation and a smaller v0.1.0 scope over permanent side-by-side model testing.

- One active model uses the GX10's full GPU capacity and avoids avoidable resource contention.
- The deployment does not need GPU sharing policy, per-model memory partitioning, or multi-model capacity management.
- Production behavior is easier to observe, benchmark, secure, and troubleshoot.
- Planned interruption during model testing or rollback is acceptable for this service.
- The model-release definition in Git makes switching and rollback explicit, reviewable, and repeatable.

## Consequences

### Accepted trade-offs

- There is no permanently active staging or candidate model.
- Users cannot compare two distinct base models side by side at the same time.
- Model changes are not zero-downtime because the current vLLM pod is replaced before the next one is ready.
- A failed or unsuitable candidate is recovered by restoring the previous Git-defined release.

### Benefits

- One namespace, one Helm release, one active vLLM Deployment, and one full-GPU request.
- Stable API endpoint and stable LiteLLM alias for clients.
- Git history is the audit trail for model selection, release settings, and rollback.
- Argo CD remains the only application deployer; the existing GitLab CI validates desired-state changes and builds images only when custom deployment code changes.

## Revisit conditions

Revisit this decision when at least one of these becomes true:

- A second GX10 or separate GPU host is available for staging.
- Continuous side-by-side user testing becomes a real requirement.
- The service needs materially higher availability or zero-downtime model changes.
- Benchmarks demonstrate that concurrent model serving meets the required latency, reliability, and operational boundaries.

Until then, multi-model serving remains deferred rather than prohibited.
